## Task 1 — the free-row predicate, server side

**Invariant:** a free row never advances a plan, and no other row stops
advancing because of this change.

Three server sites move, and they must agree because they will share one
helper:

- `routes/data.ts:1285` — `isWorkoutType(body.workoutType)` currently 400s
  anything outside `AN|O2|AT|TR`. It must admit `null`.
- `routes/data.ts:1491` — `steps must be a non-empty array` must admit `[]`
  **iff the row is a free row**.
- The plan-advance path (`stores/logs.ts:700`, `routes/data.ts:1534`) must
  refuse to set `planKey`/`planIndex` for a free row regardless of what
  `advancesPlan` says.

**Define the predicate ONCE**, server-side, and have all three call it. Two
rules keyed on the same fact that are written twice will drift; a reviewer
should have to hold one predicate, not three.

**The test table is the point of this task.** All three rows, and the second
and third are the regressions — the first is the easy one:

| Row | `workout_id` | `workout_type` | Expected |
| --- | --- | --- | --- |
| Free row | null | null | refused; `done_n` unchanged |
| Deleted-workout retry | null | `"O2"` | **advances** |
| Unmatched phone timer | set | `"O2"` | **advances** |

Row 2 is not hypothetical. `LogSession.tsx:780-790` retries a save with
`workoutId: null` when the server 400s specifically on `workoutId` — the
workout was deleted between the door's mount and the Save click. That is a
legitimate plan-advancing session posting a null workout id, and it is
exactly why the predicate is a pair.

**The independent mutation for criterion 1:** flip the refusal off and watch
`done_n` move. Criterion 1's *delete* half cannot serve as a second gate —
`delete()` returns `unCounted: false` whenever `deletedRow.planKey === null`,
which the create-side refusal already forces (`stores/logs.ts:700-712`), so
it asserts the create path twice. Keep it as a regression pin and say in the
report that it is dependent.

Integration tests need Docker (`pnpm test --project integration`).

## Task 2 — the read side: badge, type widening, AVG SPLIT fallback

**Invariant:** a stored row with a null type and no steps renders honestly
on every screen, and both screens showing an average split show the same
one.

Three changes, all read-side, all shipping before any writer exists (the
same R-A ordering `drizzle/0009_brief_kingpin.sql`'s own header describes).

**a. Client type widening.** `DROP NOT NULL` makes Drizzle infer `string |
null`, and the compiler will walk you through `LogInput.workoutType`
(`stores/logs.ts:114`) and `PlanLink.workoutType` (`:356`). Follow it.

**b. The badge fallback, asserted STRUCTURALLY.** Exit criterion 2 forbids
an empty badge, and a contrast assertion cannot convict one. Two different
failures:

- an unknown STRING renders invisible text (`--on-color` #fffdf7 on `--page`
  #f4f1e8 = 1.110:1, and 1.000:1 on `--surface`);
- `null` renders NOTHING inside a `display: inline-block` span with
  `padding: 3px 7px` and no background declaration (`index.css:509-516`) —
  an empty padded gap.

So: **assert no `.type-badge` element in the DOM at all** for the null case,
and a neutral badge at ≥4.5:1 for an unknown string. Compute the ratio and
put the number in the report (recurring failure 6).

**c. The AVG SPLIT fallback (F1).** `storedSummary.ts:671`'s TIER B1 derives
the hero from `tierBAvgSplitSeconds(row.steps)`, which returns `undefined`
on `[]` (`:519` — `d` never leaves 0), while the history list falls through
to the stored column (`LogRow.tsx:154`). Same row, two screens, one number
present and one absent. TIER B1 must fall back to the stored
`avg_split_seconds` when `steps` carries no PM5-sourced rows.

**Exit criterion 7 is the gate, and it must pin both screens together:**
assert the same figure on the list and the detail screen, then mutate the
stored column and require BOTH numbers to move. A test that asserts each
screen separately would pass the defect.

## Task 3 — the `MonitorRun` shape

**Invariant:** a Just Row record round-trips through storage and the
hand-off store, and the log-steps builder returns rather than throws.

Additive on the existing v2 record — **no `v` bump**:

- `mode: "justrow"`.
- `program: { intervals: [] }`.
- **`logSeed: { steps: [], paces: {} }`** — F4. `buildMonitorLogSteps` reads
  `run.logSeed` FIRST and throws `MonitorLogSeedError` on `undefined`
  (`logDraft.ts:836-843`), before it ever compares lengths. Rev 3 named only
  the program half of a vetted seed/program pair. Without the seed the throw
  surfaces at `summaryModel.ts:973` and is swallowed by `LogSession.tsx:387`'s
  condition-4 `catch`, silently disqualifying the record.

**Be honest in the report that this field buys nothing until PR 2** — there
is no writer and no reader for `mode` in this PR. The one thing PR 1 can
gate is `isMonitorRun`'s unknown-key tolerance, and that mutation does bite
(add an unknown-key rejection and it goes red), so it is a real gate, not
decoration.
