### Task 2: The programming lifecycle — clear, send, verify

**Files:** Modify `app/src/monitor/driver.ts`,
`app/domain/monitor/types.ts` (the `ProgramRejection` reason union +
`DriverOptions.verifyTicks`), `app/domain/monitor/pm5/commands.ts` (the
clear sequence, if it needs its own builder), tests beside each.

**Interfaces produced (Task 4's fake consumes these):**
```ts
// types.ts
export type ProgramRejectionReason =
  | "nak" | "disconnected" | "timeout" | "not-observed";
export interface DriverOptions {
  ackTimeout?: { ticks: number };
  verifyTicks?: number;   // separate bound: a SLOW monitor and a SILENT
                          // one must not produce the same failure
}
```

`program(p)`:
1. **Clear** — send the clear sequence first. A `0x81` here is EXPECTED
   (the PM rejects a terminate when nothing is running — observed §18)
   and logs `clear-rejected` as informational, never an error, never a
   throw. Cite §18 at the call site.
2. **Send** — the existing ack-gated sequencing, unchanged.
3. **Verify** — after the ack, await status frames showing
   `state === "armed"` AND the machine reporting the programmed
   structure; bound by `verifyTicks` (tick-driven, no wall clock).
   Expiry → `ProgramRejectionError` with `reason: "not-observed"` and the
   full trace.

`MonitorDriver.program`'s JSDoc states the destructive fact plainly: a
rejected program can wipe a loaded workout (observed §18), so callers
must warn BEFORE programming.

Tests that must fail against today's code: clear-rejected still programs;
verify-times-out → `not-observed` (not a false success); the happy path
resolves only after the machine reports armed; a send that acks `0x01`
but never appears → `not-observed` (D2's exact silent failure). Full
gates. Commit: `feat: program() proves it, then says so`.

### Task 3: Index normalization

**Files:** Create `app/domain/monitor/pm5/intervalIndex.ts` (+test);
Modify `app/src/monitor/driver.ts` (normalize at frame emission and at
`IntervalActual` emission), tests.

**Interfaces produced:**
```ts
export function toProgramIndex(
  machineIndex: number,
  machineState: MonitorFrame["state"],
  programLength: number,
): number | null;
```

Rule from the observed trace (§18): work reports its own index; a rest
reports the index it is heading INTO. So program index = `machineIndex`
during `rowing`, `machineIndex - 1` during `resting`, clamped to
`[0, programLength - 1]`; `null` when the value cannot be explained by
the program's length — and that case logs `divergence` (the entry that
should have fired this session and didn't, because both machine fields
agreed with each other while both differed from ours).

`MonitorFrame.intervalIndex` and `IntervalActual.index` carry OUR index
after this task; the raw machine value appears only in the event log
(`notify`/`divergence` details). Tests: the full table for a 2-interval
program including the observed `index: 2` end case → our `1`; the clamps;
the unexplainable case → `null` + `divergence`; a 1-interval program.
100% on the new file. Full gates. Commit:
`feat: the machine counts its way, we keep ours`.
