## Verdict and scale

The deciding cost scenario is five synthetic household users/sessions/grants/link attempts plus 511 live anonymous attempts, not five anonymous attempts. The anonymous limit is independently reachable without accounts. The specification's approved bounds are 120 anonymous starts/minute, 512 live anonymous attempts, one link attempt per original session, five-minute expiry and startup/minute cleanup (spec `Stored shapes and query contract`, quoted: “The database additionally caps live anonymous attempts at 512.”).

The 1k/100k/1M columns deliberately put that many rows into EACH of users, sessions, grants and live link attempts, plus 511 anonymous attempts. They measure sensitivity, not a claim that a million users or simultaneously active links exist. The only growth-sensitive auth SELECT is the signin count: it scans the link population too. It is 0.040 ms at the deciding scenario, so this review does not recommend an additional purpose index or invent a population trigger. No `session_logs` scale was used to decide an auth query. Actual production auth counts and host CPU/RAM are UNTESTED; all seeded counts are synthetic and recorded in `results.json`. The empty isolated DB began with zero users before seeding.

The lock conflict rules the correctness verdict regardless of population: it required one link attempt and one session. Passing the corrected held-order test closes that measured blocker; it is not a universal proof against every possible interleaving.
