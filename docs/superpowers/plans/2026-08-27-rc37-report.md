Spec: `docs/superpowers/specs/2026-08-27-link-authority-design.md` (rev 5, `[R5]`).

## What was built

**Part 1 — the detector** (`app/src/monitor/driver.ts`). A second, persistent
structure comparator (`armedWatch`/`armedWatchFired`) that runs on every
GENERAL_STATUS tick outside a verify phase (`pendingVerify === null`), for as
long as `armedProgram() !== null`. Gated on `state === "armed"`; compares
against `expectedArmedStructure(armedProgram())`, never a literal `8`. Uses
BOTH `STRUCTURE_MISMATCH_TICKS` and `STRUCTURE_MISMATCH_WINDOW_MS`. Emits a
new `MonitorEvent` (`{ kind: "programDropped" }`, added to
`domain/monitor/types.ts`) and logs `structure-left` once both thresholds are
met; logs `structure-mismatch-recovered` on either exit from a started streak
(self-correction or leaving "armed") that never reached both thresholds.
Reset alongside the driver's other per-run state on every successful
`program()`. Idempotent (`armedWatchFired`) against stale post-detection
ticks. ~130 lines net, not ~50 — see "What I found that contradicted the
brief" below for why.

**Part 2 — the consumer** (`app/src/monitor/useMonitorSession.ts` +, contrary
to the brief's file estimate, `app/src/workout/ConnectedInterstitial.tsx` and
`domain/monitor/types.ts`). On `programDropped`, guarded to
`phase === "programming" || phase === "ready"` (the same states `cancel()`
itself is valid from): unsubscribes, drops `driverRef`, disconnects
best-effort — **no terminate call** — and flips `phase`/`programDropped` in
one `update()`. A new `session.programDropped` boolean is exposed;
`ConnectedInterstitial.tsx` gained one `useEffect` that calls `onExit()` when
it flips true — the one step the hook itself cannot do, since `onExit` never
reaches it. No row: a pre-row session opens no record at all
(`createMonitorRun`'s single call site, gated on `phase === "ready"`).
Nudges survive because `WorkoutDetailView` never unmounts.

**Part 3** (`useMonitorSession.ts`, `endSession`): `|| linkGone` deleted from
the terminate guard, exactly as specified — one line, two tests.

## What I found that contradicted the brief — reported, not silently worked around

1. **Part 1 is ~130 lines, not ~50.** The estimate undercounted the doc
   comments this codebase's own convention requires (every constant/branch
   here carries a "why", not just a "what" — see the file's existing style)
   and the near-miss handling on BOTH exits (self-correction and
   leaving-armed), which the brief's own prose asks for but its line
   estimate didn't budget.
2. **Part 2 could not stay inside `useMonitorSession.ts`.** Reaching
   `onExit()` — the destination the brief itself names as load-bearing
   ("the destination is `WorkoutDetail`... never `onEnded`'s post-session
   flow") — is structurally impossible from inside the hook: `onExit` is a
   prop the hook never receives, and setting `phase: "ended"` to route
   through the EXISTING "ended" handling would land on `onEnded`'s post-
   session log screen instead — the wrong destination, explicitly forbidden
   ("Do not invent a new screen... that bypasses it"). The only way to reach
   the SAME `onExit()` handleCancel reaches was a new `session.programDropped`
   boolean plus one small `ConnectedInterstitial.tsx` effect that calls
   `onExit()` directly. This also required a new `MonitorEvent` member
   (`domain/monitor/types.ts`) as the driver→hook signalling seam — there is
   no other way for the driver to tell the hook anything. Neither touches a
   stored shape, a pgEnum, or a migration — the "no stored shape" constraint
   is intact; only the *file* constraint was too narrow.
3. **"Carry EXPECTED and OBSERVED (all four fields)"** — `ArmedStructure`
   has exactly three fields (`workoutType`, `workoutDurationRaw`,
   `workoutDurationType`); there is no fourth. I reused the EXISTING
   `describeStructureMismatch` helper, whose own doc comment says "all
   three fields explicitly" — the same idiom `verifyArmed`'s own
   `structure-mismatch` entry already uses, so a `structure-left` entry
   reads identically to its sibling. Read as an imprecise brief, not a real
   fourth field to invent.
4. **`endSession()`'s own guard (`cancel()`'s twin) needed no change** —
   confirmed by reading, not assumed: `cancel()`'s `armed` check already
   depends on `driver !== null`, and the `programDropped` handler nulls
   `driverRef` itself, so no interaction between the two paths was possible
   to introduce.

Everything else in the brief was followed verbatim: no stored shape, no
pgEnum, no migration, no new copy, the `armed` gate kept, both constants
used, compare against what we sent.

### driver.ts — Part 1

1. **Armed gate** (`const armed = toMonitorFrame(...).state === "armed"` →
   `const armed = true`). Red: the dedicated armed-gate test AND
   `walk-2026-08-25/rests-finished`'s own negative-corpus test — a REAL rest
   boundary now falsely fired `structure-left` (`5 consecutive armed
   tick(s) over 2070.9ms... observed durationRaw=500 durationType=128;
   expected durationRaw=6000 durationType=0`). Re-ran with the same
   mutation against the **pyramid** capture too (added mid-task, see
   below): also caught it, on interval 2's own boundary (`durationRaw=700`
   vs expected `300`) — two independent real captures both convict the same
   mutant. Restored; both green.
2. **Window half removed** (`mismatchStreak >= TICKS && heldMs >= WINDOW`
   → `mismatchStreak >= TICKS`). Red: "pins BOTH constants (1 of 2)" (a
   600ms-held 3-tick streak wrongly fired) and "the near-miss (1 of 2)"
   (self-correction test — the streak fired before the correcting tick
   could ever arrive). Restored; green.
3. **Tick-count half removed** (`... && heldMs >= WINDOW` → `heldMs >=
   WINDOW` alone). **First attempt found a real gap**: the existing "pins
   BOTH constants (2 of 2)" test (alternating payloads) did NOT catch this
   — an alternating payload resets `mismatchSince` on every tick regardless
   of whether the tick-count half is even checked, so `heldMs` never clears
   the window either way. Added a NEW test ("pins BOTH constants (3 of 3)":
   the SAME wrong structure, 2 ticks, 2500ms apart) that isolates the other
   shape. Re-ran the mutation: the new test correctly went red (`2
   consecutive armed tick(s) over 2500ms`), the old one stayed green
   (proving it tests something real, just not this). Restored; both green.
   **This is documented per the mutation-probe convention — the gap the
   probe found is now closed, not just noted.**
4. **`armedWatchFired` guard removed** (`else if (!armedWatchFired)` →
   `else if (true)`). Red: the driver-level "fires... exactly once" test
   (2 entries instead of 1) AND the real-capture positive replay (20
   `structure-left` entries instead of 1, across the 112-frame mismatch —
   the idempotence guard matters most exactly on a real long-held
   mismatch). Restored; both green.
5. **Near-miss log on the leaving-armed exit disabled**
   (`if (armedWatch.mismatchStreak > 0)` → `if (false)` on the `!armed`
   branch). Red: "the near-miss (2 of 2)" (0 entries instead of 1).
   Restored; green.
6. **Near-miss log on the self-correction exit disabled** (same guard on
   the matching-structure branch → `if (false)`). Red: "the near-miss (1 of
   2)" (0 entries instead of 1). Restored; green.
7. **Per-run reset removed** (`armedWatch = {...}; armedWatchFired = false;`

+ `domain/monitor/pm5/framer.ts#reassemble` — the exact inverse of
`pm5/commands.ts#buildProgrammingSequence`. Every capture's `divergences`

positive) — proof the transcriptions are byte-exact, not just plausible.

`armedFrameCount` is an INDEPENDENT oracle — computed directly off each
capture's own raw 0x0031 bytes via `parseGeneralStatus`/`toMonitorState`,
never off anything the driver-under-test decided, mirroring the "300 armed
frames" methodology the design spec's own §1 cites (applied per-capture here
rather than only as a corpus-wide total). 474 armed frames across five
genuinely healthy sessions, **zero** false detections and **zero** near-miss
recoveries — the margin is clean, not merely lucky: no capture ever produced
even a single armed-tick mismatch to recover FROM. **There is nothing here
for the hardware walk's near-miss reading to report** (the design spec's own
instruction, §1b: "if a rest-bearing piece produces
`structure-mismatch-recovered` entries at all, say so... it is the
measurement that decides whether the thresholds are comfortable or lucky")
— on this evidence they read comfortable, not lucky, though this is REPLAY
evidence only; the design spec's own exit criterion 5 (a rowed hardware leg)
is what actually settles it, and that walk has not happened.

The positive capture (`menu-at-ready`) fires exactly once, on
`3 consecutive armed tick(s) over 2000ms` reaching the same threshold
combination the README's own decode recorded holding for 112 frames /
56.4s in the real walk — this replay only needs the first 3 ticks past both
thresholds to prove the detector, not the full 112.
