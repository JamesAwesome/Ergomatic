## Part 1 — the detector (`app/src/monitor/driver.ts`, ~50 lines)

Today `verifyArmed`'s structure comparison runs only during the verify phase
— its own note: *"one entry per verify phase, never per tick"*. Extend the
comparison to run for as long as the machine reports `armed`.

**This is a NEW comparator, not a lifetime extension, and the plan should say
so in a comment.** The existing state (`mismatchStreak`, `mismatchSince`,
`expected`) lives on `pendingVerify`, which is assigned once in `verifyArmed`
and nulled on resolve. You need persistent state plus a retained
`expectedArmedStructure(p)`.

**Three constraints, each with a reason you must not relax:**

1. **KEEP THE `armed` GATE** (`driver.ts:4767`, `state === "armed"`). The
   structural quadruple legitimately moves mid-session — `rests-finished`
   goes `durRaw 6000 -> 500` with `durType 0 -> 128`. Filtered to armed
   frames across four healthy captures: **300 frames, ZERO mismatches**.
   Without the gate an always-on comparator would end live rows.
2. **USE BOTH CONSTANTS.** `STRUCTURE_MISMATCH_TICKS` (3) **and**
   `STRUCTURE_MISMATCH_WINDOW_MS`. That constant's own doc comment says it is
   *"NO LONGER SUFFICIENT ON ITS OWN (hardware walk 5)… carries only the
   STABILITY half… and a rejection needs both."* Reusing one half is the
   false economy an antagonist pass already caught in this spec.
3. **Compare against what we SENT, never a literal `8`.**
   `expectedArmedStructure(p)` already does this. `8` is our compiler's
   choice, not a PM5 universal, and we have read exactly one row of
   `OBJ_WORKOUTTYPE_T` — the check does not need to know what `1` means.

No aggressive threshold is needed: in the capture the wrong structure holds
**112 consecutive frames over 56.4 s**.

### The ring entries — build the instrument in the same change

James: *"Make sure if we need to add anything to monitor log to make
debugging easy we do."*

1. **`structure-left`** — the detector fired. Carry EXPECTED and OBSERVED
   (all four fields), the streak length, and the elapsed window.
2. **`structure-mismatch-recovered`** — a mismatch that started and went away
   WITHOUT reaching both thresholds. **This is the near-miss and it is the
   most important entry here.** Without it, "the detector stayed silent
   through the piece" cannot be distinguished from "it mismatched twice at
   every rest boundary and got lucky on the thresholds". Carry the streak
   reached and the window elapsed so the margin is readable.
3. The existing **`structure`** entry already logs on change. Leave it.

**Throttle: log the START of a streak and its RESOLUTION, never per tick.**
Status ticks arrive at ~2 Hz into a 500-entry ring; `refusedKeysLogged` and
the stale-count rest clamp in this same file are the idiom to copy.

## Part 2 — the consumer (`app/src/monitor/useMonitorSession.ts`, ~20 lines)

On a sustained mismatch: **end the session and exit exactly the way Cancel
does.**

`ConnectedInterstitial.tsx:335-338` is the shape:
```ts
function handleCancel(): void {
  void session.cancel();
  onExit();
}
```
`onExit()` reaches `WorkoutDetail.tsx:281`'s `handleInterstitialExit`, which
is `setConnecting(null)` — the workout screen with **Connect**, the last-used
PM5, and the block still on it.

**Wiring is your call**, but the destination must be the SAME one
`handleCancel` reaches. Do not invent a new screen, a new phase, or a new
prop that bypasses it.

**No row is written.** A pre-row session opens no record — that is Phase LM's
own finding — so there is nothing to save and nothing to discard.

**No terminate is sent.** The machine has already left; there is no program
to terminate.

### Nudges must survive, and there is already a test-shaped claim to pin

`nudges` is `useState` on `WorkoutDetailView`, which is keyed
`key={workout.id}` so it resets only on a workout SWITCH
(`WorkoutDetail.tsx:123-126`). Exiting the interstitial keeps the component
mounted, so nudged targets should still be on screen.

**Verified by reading, but pin it with a test anyway** — it is the half of
James's ruling a future refactor could silently break.

## Part 3 — End always terminates. One line.

`useMonitorSession.ts:3155`:
```ts
if (driver === null || linkGone) return;
```
Delete `|| linkGone`.

Today a false link-lost latch means the rower presses End, the app closes the
record, and **the erg keeps running while they are standing at it**. Attended
human intent is not a verdict. If the link genuinely is gone, `terminate()`
throws into the existing catch, which is already best-effort by design.

Plus two tests: End terminates with `frameSilence` latched, and the existing
link-up behaviour is unchanged.
