Concept2 connect + send — Gate 0 amendment

2026-09-03 · Wave E PR2 · amends the board approved 2026-08-31 (docs/design/handoffs/2026-08-31-concept2-connect/README.md, Concept2 connect.dc.html). Every frame below is at real proportions: 390×844 portrait, 844×390 landscape. Colour values are app/src/theme/tokens.css's, verbatim; contrast is computed (WCAG relative luminance) and printed in the last section.

Frames are badged UNCHANGED (the approved board, reproduced for comparison), CHANGED (approved copy or shape that this amendment moves, with the reason and the file:line that forces it), and NEW (a state the board has no frame for). Nothing here is implemented. This document IS the gate.

Why an amendment at all. The board was approved before PR1, PR1.5, PR1.75a and PR1.75b existed. Four of its frames describe behaviour the shipped server and native code cannot produce, and several states the shipped code CAN reach have no frame. Each is named below with the line that settles it.

Type FACES on this page are system stacks. The app ships Newsreader / Archivo / IBM Plex Mono; sizes, weights, tracking and colour are the app's, glyph shapes are not. Mono tracking reads slightly wider here.

1 1a's weight-class ask is conditional: "do NOT ask H/L if Concept2 already has a weight class on the account." There is no ask at all. The WEIGHT CLASS section, its segmented control and its helper are gone; Connect is live on first paint. One helper line replaces them: "Your weight class comes from Concept2." It names CONCEPT2 rather than the profile, because the profile is only the fallback producer and this card cannot open it. James, 2026-09-03: "I don't want that set in our app. I want it to be set on Concept2's side." Measured the same day on log-dev: a result POSTed without weight_class is refused 422 ({"errors":{"weight_class":["The weight class field is required."]}}), and GET /api/users/me carries weight and gender but no weight_class — so the class is READ FROM CONCEPT2 at send time and stored by us nowhere. Corrected 2026-09-03: an earlier revision of this row said "derived", which named the wrong producer. Concept2's own help says the rower designates the class per piece, so the server reads their most recent declaration first and derives from the profile only as a fallback (see 2i and 2c). Supersedes both the board's conditional ask and this amendment's earlier "unconditional" answer.
2 1c Linked is "just LINKED ✓, helper line, unlink". Adds an identity line naming both principals. ROADMAP's C2-account-injection row: "detect-identity treatment (the callback/linked card naming which account the link goes to) ships with PR2's surface".
3 1b carries a Cancel button, and a second "CONFIRMING THE LINK / Checking the link with Concept2" variant. Both removed. One panel, no buttons. Native: the consent sheet covers the app, so nothing behind it is tappable and the outcome arrives in startLink's promise (adapters/linkFlow.ts:282-333). Web: openExternalUrl is window.location.assign (adapters/webNavigate.ts), so the document unloads. Neither surface can present a Cancel or a confirming state to a rower.
4 2c Sent line reads "Accepted by Concept2 · Aug 27, 11:31". "Accepted by Concept2." — no timestamp. Nothing stores one. session_logs gained exactly c2_result_id and c2_user_id (server/db/schema.ts:377-378); there is no acceptance timestamp column and inventing one from loggedAt would print a different event's clock.
5 2d Duplicate's link-out reads "Open your Concept2 logbook →" (generic). "View on Concept2 →" with the result id, same as 2c. C2's 409 body names the colliding id and the route stores it before responding (server/routes/concept2.ts:890-898), so the specific row is reachable. Also: 2d is session-transient — after any remount the row reads SENT (2c), because that write is durable.
7 2c Sent shows the result id and nothing about the class. A second mono sub-line naming the class that was sent and which producer supplied it — "WEIGHT CLASS H · FROM YOUR LAST CONCEPT2 ROW" or "… FROM YOUR CONCEPT2 WEIGHT". Session-scoped: nothing about the class is stored, so a later visit renders 2c without it. Concept2's help makes the class the rower's declaration, so a class we DERIVED is a guess written to a permanent third-party record. Concept2 permits per-result editing, so a guess the rower can see is one they can fix. A guess nobody sees is one nothing can catch (RF11).
9 The declaration is read from Concept2's results list as it comes. The read excludes every result id this app wrote, and a page whose only rows are ours counts as NO declaration — so row 7's line cannot relabel our own guess as the rower's declaration. Concept2's list contains the rows we posted, its 201 echoes the class we sent, and nothing on the row marks it as ours. Send 1 derives and says so; send 2 would have read that same class back and said "FROM YOUR LAST CONCEPT2 ROW", silencing the one line that makes the guess correctable. Reading our own writes back as an oracle is RF11 one level up.
10 2i's sentences name where to go, one per reason. All three say "open Concept2 to check it", and the shared middle sentence says what WE could not do rather than what the rower should fix. One sentence sent the rower to pick a class "on a result in your Concept2 logbook" beneath a button that opens the profile, where it cannot be picked. And an implausible weight is most likely our own unit inference being wrong, so blaming their weight sends them after a field that is probably fine.
11 Copy carries a second clause that reassures, or repeats a control already on screen: "… · YOU COME BACK HERE", "… · OPENS YOUR CONCEPT2 LOGBOOK", "Nothing changed.", "This row is unchanged.", "… then send this row again." Every rendered string is mechanical: it says what is true, once. The footnote is "OPENS CONCEPT2 IN YOUR BROWSER"; the id line is "RESULT 339"; the failure is "The send didn't reach Concept2."; the refusals are two short clauses ("Concept2 needs a weight class. Your Concept2 profile has no weight set.") naming no destination. James, 2026-09-03: "check the prose and make it a bit more mechanical … that can just be 'OPENS CONCEPT2 IN YOUR BROWSER'". Each dropped clause was either reassurance the rower did not ask for, or a restatement of a control already on screen — the Send again button says send again, and View on Concept2 says where it opens. Supersedes the board's "copy is final as rendered" note for these strings.
12 Three REASON lines end in a wire token, uppercased: "… · NOT MONITOR" from not_monitor, and "… · NOWINDOW" / "… · CANNOTSTART" from a LinkOutcome kind and a Capacitor error code. Every token gets words written for a rower, or is dropped. NO MONITOR USED · DIDN'T FINISH · NO WORK TIME OR METERS for the three eligibility tokens; one sentence, "THIS DEVICE COULDN'T OPEN CONCEPT2", for all four device-open failures. Also "CONCEPT2 REFUSED THE LINK", not "THE EXCHANGE" (an OAuth word, not a rowing one), and "THE BROWSER LEFT CONCEPT2". James, 2026-09-03: "'REASON: CONCEPT2 WON'T TAKE THIS ROW · NOT MONITOR' is a bit awkward … I'd check for similar prose awkwardness." It read that way because nobody wrote it: the line appended reason.toUpperCase().replace(/_/g, " "), so an enum member became copy. It keeps a "Send again", targets the id-less {origin}/profile, and carries three sentences for the route's four reasons. The frame's own copy said "send this row again" and gave no way to; the link-out returns to a still-mounted block on native. The id-bearing path was MEASURED to render a public read-only card with no weight and no form. 6 The 401/403 callback pages say "Sign in to Ergomatic here" — where "here" is plain text, no anchor. Reworded so no word poses as a link. server/concept2/callbackPage.ts:52-56: the template emits no anchors and no subresources on purpose (the callback URL carries code; RFC 9700 §4.2). An earlier revision of this amendment drew a state (1k) for a stored weight class that could not be read back — a RECONNECT button nothing could press, plus a re-ask to rescue it. 1h Unavailable NEW

{available: false} arrives with HTTP 200 (server/routes/concept2.ts:524-529) — a flag-off server reads exactly like an unlinked one unless the client distinguishes them, which is the trap Concept2LinkProbe.tsx:118-121 already names. A failed READ is not this state, and an earlier revision of this page said it was. The two are separated below as 1i, which has its own copy, its own REASON and a Retry. The pre-first-read case keeps 1h's silence, because nothing is yet known and there is nothing to say.

5 · Accent's fifth job, declared

docs/design/handoffs/2026-08-03-ui-fix/DESIGN.md:39-41: "Accent red now means exactly four things: the level-1 action, a resolved split or duration, a destructive control, the active tab mark."

Unlink is job 3 and needs no dispensation. "View on Concept2 →" is not any of the four. The precedent for a fifth candidate is --action-connect (src/theme/tokens.css:33-41), which was given its own token rather than made accent's fifth meaning. Two ways to settle it, and PR2 must pick one rather than quietly painting a fifth thing red:

  • Accept it as a documented deviation — the board rendered it in #b5341f and James approved that render on 2026-08-31; record a DEVIATIONS.md row saying accent now also means "leaves the app for the rower's own record". One row, no token, no repaint.
  • Give it --ink with an underline — keeps the four-meaning rule literally true; costs the link-out its visual pull on a screen that has no other coloured element.

Recommended: the first. The rule's purpose is that accent not become "selected" or a fifth workout type; a single link-out on one screen is a different kind of exception, and the alternative is a token nothing else would ever use.
