The screen you meet when the phone won’t keep the run

Countdown.tsx builds and saves a SessionRun the instant baselines and preferences are ready (the mount effect, line 219‑220), then starts counting down. saveRun already returns a boolean for exactly this (run.ts:184, the same shape saveDraft uses) — the effect calls it and throws the result away, so a rower whose phone refuses the write watches a countdown start anyway, over a run that was never saved. This is AUD‑015, already named in CLAUDE.md’s recurring-failure 25 as a shipped instance of “a lower layer reports a durability failure and its caller proceeds as if persistence succeeded.” This gate is the screen that replaces “proceeds anyway”: the SAME shape Countdown.tsx already renders twice, for its own baselines/preferences load failures, with one new message and its existing Cancel button added.

Tokens are app/src/theme/tokens.css verbatim; every frame class is copied from app/src/index.css by name with unchanged values (each block above says which lines). Frames are 372×640 portrait and 720×340 landscape, the sizes Gate 0-A/B used. Fixture: Tropical Wave, the seeded 5 × 500 m at 2k + 2 workout Gate 0-B already used, so its numbers (1:52.0 target split) carry over unchanged. Every ratio below is the WCAG relative-luminance formula, computed with the same script Gate 0-A/B used. Nothing is implemented.

What I am asking you to approve

Four decisions. The frames are the argument; these are the asks. Every word is a draft you can reword — the shape is what needs your eyes.

(a) The message’s words

Countdown.tsx’s two existing failures read Couldn’t load your baselines. and Couldn’t load your preferences. — same shape, same length, no second sentence (the button already says what to do). This is a third member of that family: Couldn’t keep your session on this phone.

Word choice, not invention. “Keep” is already the app’s own word for a session record surviving a phone (ConnectedSurface.tsx’s COULD NOT KEEP THE RECORD ON THIS PHONE., the lost banner’s N intervals kept. / Nothing kept.) — reusing it here says the same true thing a rower has already been told once before, rather than teaching a second word for one idea. No technical term appears: not storage, not quota, not localStorage.

(b) Retry + Cancel as the pair, and why “Row anyway” is deliberately absent

The two controls are the same instances the screen already has: .button-outline Retry (this failure’s own shape) and .countdown-cancel Cancel (the counting screen’s own, unchanged — same handler, same copy). No third button.

“Row anyway” would mean starting the countdown over a run that exists only in memory, never written. Both screens that come next read their run from storage at mount, once, and never fall back to anything held in memory: Timer.tsx:376 (useState(() => loadRun())) and LogSession.tsx:1232 (the identical lazy read). Timer.tsx:493 is explicit about what a missing run does — if (run === null …) return <Navigate to="/today" replace />. A rower who rowed anyway would count down, start pulling, and get bounced to Today the moment they next reload, backgrounded the phone, or the live timer itself re-reads — silently, with no session behind it. Cancel, which already exists and already clears both the draft and any run cleanly, is the only honest second control.

(c) Retry restarts the count, it does not resume one

Retry re-invokes the same build effect — buildRun + saveRun — the way baselinesState.retry already does for its own error today. buildRun stamps startedAtMs at the instant it runs (Countdown.tsx:203‑204), so a Retry that lands is, structurally, the exact case the component’s own doc comment already names and accepts: “a reload while counting down rebuilds and re‑saves the run and restarts the count … this is deliberate (spec Resilience 4).” Nothing new is invented to make this true; it falls out of the effect that already exists.

3 · Two failures, side by side — which is which

Both are real, shipped-or-proposed error states that can fire for the same attempt to start Tropical Wave. They are not duplicates of one idea; they are two different writes, one screen apart, and each one knows something the other does not.

WorkoutDetail shipped today · the DRAFT write

TROPICAL WAVE

Start Timer

Couldn’t start this session. Try again.

useStartWorkout.ts’s confirmReplace: saveDraft(draft) fails, before any run exists. The rower is still on the workout’s own detail page, has not committed to anything yet, and every other control on the page (Connect, nudges, the type chip) is still right there. Pressing Start Timer again re-runs the same check.

Countdown this gate · the RUN write

Couldn’t keep your session on this phone.

Countdown.tsx’s build effect: saveRun(run) fails, one screen later — the draft already saved, the rower already pressed Start and left the workout page behind. There is no page to fall back to here; Cancel is the only way out, and it is the same Cancel the counting screen already ships (clears the draft and any run, returns to the workout or Today).

What each screen knows that the other does not. WorkoutDetail knows the rower has not committed — nothing downstream expects a run yet, so its own retry is just “press Start again.” Countdown knows the opposite: the draft is real, startedAt is stamped, and the rower believes they are seconds from rowing. Its failure is later in the sequence and closer to the erg, which is why decision (b) above treats “proceed anyway” as unsafe here in a way WorkoutDetail’s own retry never had to consider.
